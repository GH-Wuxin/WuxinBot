# OSU Analyze 审查流水线设计（2026-08-01 讨论定稿）

状态：**已拍板，待实现**。当前优先级低于正在处理的紧急 bug，实现前先读本文。

## 背景

上一轮流水线重构解决了数字准确性、Mod 语义统计、PP+ 去 clamp 等问题，但输出仍有“说了等于没说”的模板句，且 30000pp 和 3000pp 的玩家得到同样的语气。本设计解决：数据尺度感知、审查系统独立、拒绝可观测。

## 一、数据尺度知识块（生成侧提示词）

写入 `buildAnalysisEditorPrompt` / `buildAnalysisSectionCommentsPrompt`，**不改 persona.ts**。一次性注入的尺度知识：

- **rank 是主锚**：#1–100 世界顶尖；#1000 内强手；#1 万内超过绝大多数活跃玩家；#10 万外大众区间。rank 稳定、不受 PP 通胀影响，所以定强弱分量看 rank。
- **星数定风格**：6★ 以下普通主场；7–8★ 硬图常客；9★+ 高难区；10★+ 顶尖档案。
- **PP+ 定形状**：15.00 不是上限，是 LazyBot 旧量表的“专家基准线”；超出 15 表示旧量表已被顶穿，程序已提供逐项超出幅度。
- **pp 只作装饰数字**：引用让评价具体（“BP1 有 1857pp”），但不决定分量。
- **明确禁止套话**：任何“换个玩家也成立”的句子都算废话；宁可段落无评价，也不写万能句（最终兜底见第三节，实际不会留空）。
- **不硬编码档位词表**：不给“传奇档/禁词表”式方案，靠尺度知识让模型自己判断。

## 二、审查 LLM（与 pippi 完全隔开）

审查侧是独立系统，**无人格、无口吻、不模仿任何人**：

- 检查清单（只查这些）：
  - 数字与简报一致（rank、BP 数量、pp 值不编造）；
  - 统计关系正确（“含 HD”包含 HDDT/HDHRDT，禁止用完整字符串精确匹配代替语义统计）；
  - 不与简报直接矛盾（rank #1 却说“继续加油”）；
  - 空泛度（“这句话换个玩家也成立吗？”）；
  - 结构完整。
- **不检查**：文采、人格词、句式偏好、互动数量、结论里有没有数字。
- 输入：数据简报 + 待审全文。
- 输出：固定 JSON，逐段 verdict：
  ```json
  {
    "verdicts": [
      { "section": "mods", "result": "REJECT", "reason": "空泛（此句对任意玩家成立）" },
      { "section": "conclusion", "result": "PASS" }
    ]
  }
  ```
- 每次 REJECT 必须带简短、结构化的原因（用于日志与后续提示词迭代）。
- 模型独立配置：生成侧与审查侧分开，默认均可用 flash，后续可单独换。

## 三、重试循环（最终拍板）

“宁愿留空”方案被覆盖——空着影响观感，改为最多三次尝试：

```
第 1 次：pippi 生成整篇 → 送审
  ├─ 全 PASS → 输出
  └─ 有 REJECT → 带原因打回（只重写被拒段落，PASS 段原样保留）
第 2 次：重写被拒段落 → 整篇送审
  ├─ 全 PASS → 输出
  └─ 有 REJECT → 再带原因打回
第 3 次：再重写 → 送审（结果只记录，不执行打回）→ 直接放过输出
```

- **最多两次打回，第三次无论审查结果如何都放行**，保证观感上永远有内容。
- 第三次也过一遍审查，审查结果与拒绝原因全部落日志，作为后期调整提示词的依据。
- 打回重写的输入 = 段落原文 + REJECT 原因 + 数据简报。
- 数据表不受审查影响，任何时候都正常显示。

## 四、日志与可观测

- 每次审查记录：轮次、段落、PASS/REJECT、原因。
- 拒绝原因沉淀后可统计：哪类句子总被拒、尺度知识哪里没写明白。
- 控制台是否可视化“哪段被拒、为什么”**待定**（用户问过，未拍板）。

## 五、延迟账

- 最坏 6 次 LLM 调用（生成 3 + 审查 3），平均约 2 次。
- 整篇一起送审，审查只有一跳；打回重写按段进行，避免“改一句全文跟着变”。
