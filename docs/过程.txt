但不能靠复制前文混过最终重试。
这个划分比“所有规则始终同等严格”合理，也比“最后一次什么都放行”可靠。

你怀疑得对：deepseek-v4-flash 本体没有差到这个程度。现在主要是生成链把它越修越坏了，单纯开启 Thinking 也救不了。
我做了同一份 mrekk 数据的隔离测试，没有改代码、没有入库。
Thinking 测试结果：
当前完整 Prompt：约 6363 输入 token、113 行系统规则。
关闭 Thinking：约 8 秒生成正文。
开启 Thinking：约 100 秒，8192 个输出 token 全被隐藏推理耗尽，正文为空。
把 Prompt 临时压缩后再开 Thinking：约 20 秒成功输出，但变成了冷静分析师，还违反 JSON 格式、把 PP+ 写成具体能力、把 Mods 写成偏好。
所以按当前生产配置直接开启 Thinking，只会导致更多空输出和 fallback。项目现在每次生成最多给 4096 token，而实测 Thinking 连 8192 都能全部吃完。
真正的根因有四个：
Prompt 已经过载
当前七栏 Prompt 约 8000 字符，整个 analyzer.ts 的几个 Prompt 构造器累计约 208 条规则。人格要求被埋在大量“不能……不得……不要……”里面，Flash 最安全的策略自然是写冷事实。
Validator 已经出现大量误杀
v80 的 66 次初稿拒绝中：
36 次触发数字校验；
14 次触发历史句式冷却；
11 次触发最低长度。
其中存在确定的正则错误：
87 张 stream 被读成 7 张；
81 张 aim 被读成 1 张；
70 张 aim 被读成 0 张；
54 张 aim 被读成 4/6 张。
也就是说，模型明明写对数字，系统却要求它反复重写。重写到最后自然越来越怪。
每次 Analyze 实际并不独立
[commands.ts (line 223)](/REDACTED_REPO_ROOT/server/osu/commands.ts:223) 会读取最近 20 份报告，目前得到 48 条历史表达，再用三字 n-gram 相似度拒绝新稿。
更严重的是，函数接收了“排除当前玩家”的参数，却完全没有使用。相同玩家重新生成时，也可能被自己以前的好句子拦截。
这会产生一种必然退化：
正常自然表达逐渐被占用
→ 模型被迫寻找生僻替代词
→ 越生成越不像人话

坏稿被剪句后仍冒充正常 LLM 输出
三次生成都失败后，代码会删除被 validator 命中的句子。只要残余部分通过检查，就继续标记为 source: llm。Wuxin 那种冰冷数字清单正是这样来的。
结论很明确：我们确实走偏了。问题不是“限制还不够多”，而是已经形成了 Prompt、validator、历史冷却、reviewer、剪句互相打架的规则迷宫。
正确回头方向应当是：
暂时不要全局开启 Thinking。
先修数字正则误杀。
移除跨报告历史表达硬拦截，保证 Analyze 真正独立。
删除“剪句残余仍算正常 LLM”的路径。
将机械 validator 收缩到可严格证明的事实：数字、Mod、结构和明确冲突。
把文风、人格、是否有趣交还给模型，不再用正则模拟文学编辑。
大幅压缩 Prompt。
后续可以只给“分析规划器”开启 Thinking，让它先选事实和观察角度；实际文案再由非 Thinking Flash 输出。
所以这次不用怀疑 Flash 正式版本身。初稿其实经常比最终成品更有活力，是后面的审查链把它磨成了现在这个样子。

最小卡片实验出现了更关键的异常：开启官方 JSON mode 后，deepseek-v4-flash 没有生成短评，而是把输入对象原样回显，并把中文变成 ?。不开 JSON mode 时，它又无视“只输出七键 JSON”，展开成整篇模板化分析。这已经超出普通提示词调优范围。
我现在用同一官方端点的 deepseek-chat 做一次只读控制实验；不是切换生产模型，而是判断问题属于 V4 Flash 当前接口/结构化输出兼容性，还是我们自己的调用层。




控制实验还有一个结果：请求 deepseek-chat 时，上游仍返回 deepseek-v4-flash，说明官方端点当前把 chat 别名也映射到 Flash，无法作为不同模型对照。Flash 的普通文本模式会无视 JSON 要求并套“指挥官/详细报告”模板，JSON mode 又会损坏中文并回显输入。
我再试最后一个官方结构化通道——强制 function calling。若它能可靠返回七个字段，就可以用“程序提供观察卡、模型只负责选取和表达”的两阶段架构；若仍失败，就必须放弃依赖 Flash 自由生成结构化中间结果。




function calling 也不可用：模型能按 schema 调函数，但所有中文参数都会变成 ?，而且语义仍会把 PP+/分类写成能力。更离谱的是，给它一个只有一句话的“忠实改写”任务时，关闭 Thinking 的 Flash 直接回答“还没有学会回答这个问题”。
这说明 Flash 的无 Thinking 模式对短指令存在明显退化，而不仅是我们的报告 Prompt。我正在做一个最后的最小验证：相同一句话仅开启 Thinking，观察它是否恢复基本指令遵循。如果恢复，就重新评估“在选好观察卡后只给写作阶段开低档 Thinking”的成本；如果不恢复，就不能再把核心质量押在这个模型上。

Thinking 最小验证也失败了：一句 121-token 的忠实改写，开启 Thinking 后消耗 2,085 reasoning tokens，却擅自编出“Top 0.1%、手硬、冲前 3000”；萌新那句更是烧满 8,192 completion tokens后返回空内容。和四档大测试结论一致，Thinking 不能救它。
我现在验证一个可行的降级架构：让 Flash 在结构化通道中只输出英文/ASCII 的受限短评，再单独做中文忠实翻译。这样可以绕过其 function calling 中文变 ? 的接口缺陷，同时保留模型对观察卡的选择和表达；若语义仍越界，就不采用这条路。




翻译链的症结找到了：用中文写“请翻译”会触发 Flash 自行分析；用纯英文翻译系统指令时，它可以一次准确翻译八行，数字、字段和边界都能保留。
因此“英文受限写作 → 英文指令忠实翻译”在技术上可行。现在只差验证英文写作阶段能否加入足够的 pippi 活力而不添事实；如果能，这会成为比正则重试可靠得多的正式生成链。
